Link

Put a password on a link. You get back a link to share — it reveals the real destination only to someone who knows the password.

What this does

You give it a destination and a password. It gives you back a link. Anyone who opens that link is asked for the password, and only then sees where it goes.

Nothing is uploaded and nothing is stored. There is no account, no database, no server-side record. This page is a static file, and every byte of work happens in the tab you are looking at.

Why the link can carry a secret

The encrypted destination rides in the URL fragment — everything after the #. Fragments are the one part of a URL a browser never puts on the wire: they are absent from the HTTP request, from server logs, and from the Referer header. The web server that hands you this page receives a request for /link/ and nothing more.

So the encrypted destination travels inside the link itself rather than sitting on somebody's server waiting to be handed over, subpoenaed, or breached.

What this deliberately does not do

  • It is not burn-after-reading. There is no server, so there is nothing to delete after a first view. Anyone holding the link can open it again and again, indefinitely, as long as they have the password.
  • Links do not expire. There is no clock and no kill switch. A link works until the password is guessed or the link is lost.
  • It does not protect the destination itself. This hides which page you are pointing at. If that page is public and guessable, or needs no login, anyone who reaches it another way still gets in. A protected link is not access control on the far end.
  • It cannot un-send. Once the link is out, it is out.

Where the link ends up

The fragment stays off the network in transit, but the link as a whole still lands in ordinary places. Assume all of these:

  • Your browser history and the recipient's, plus the address bar of whatever tab is open.
  • The clipboard, and any clipboard-sync feature across your devices.
  • The chat, email, or ticket that carried it — including that provider's servers and backups.
  • Corporate link rewriting is the sharp edge here. Systems like Outlook Safe Links or Proofpoint URL Defense wrap an entire URL, fragment included, into a query parameter on their own domain. That folds your ciphertext into a URL that is sent to their servers and logged. It stays encrypted, but it stops being unseen.

Ordinary link previews are less of a problem: a preview fetcher requests the part before the #, so it never receives the payload — and it cannot generate a preview of the hidden destination either.

Send the password separately

This is the whole ballgame. A link and its password pasted into the same conversation are exactly as secure as sending the destination in the clear. Use a different channel and ideally a different device — the link by email, the password by phone.

How it is encrypted

  • Key derivation: PBKDF2-HMAC-SHA256, 600,000 iterations, over a fresh 16-byte random salt every time. That is the current OWASP floor for PBKDF2-SHA256. Passwords are normalised to Unicode NFC first, so a link made on a Mac still opens on Windows.
  • Cipher: AES-256-GCM with a fresh 12-byte random IV. GCM is authenticated, so a link that was truncated or edited in transit is refused rather than decrypted into garbage.
  • Header binding: the message header (version, KDF parameters, salt, IV) is passed as GCM additional authenticated data, so nobody can splice a ciphertext onto a different header — for example to downgrade the iteration count — without the tag failing.
  • Length hiding: the destination is length-prefixed and padded to a 256-byte boundary before encryption, so the link's length does not reveal how long the destination URL is.
  • Randomness comes only from crypto.getRandomValues. Salt and IV are regenerated every time, so neither is ever reused.

One honest caveat on the key derivation: Argon2id would be the better choice, because being memory-hard it resists GPU cracking far better than PBKDF2 does. No browser implements it natively, so using it would mean shipping a WebAssembly library — and this site deliberately runs zero third-party code. PBKDF2 at the OWASP iteration floor is the strongest option available without that trade.

Only http and https destinations

Both when a link is made and again when one is opened, the destination is parsed and its scheme checked against a strict allowlist. This is a real security control, not tidiness: a hand-crafted link could otherwise carry a javascript: destination, and rendering that as something you can click would run its code on this page. Anything that is not http or https is shown to you as plain text and never as a clickable link.

You are always shown the full destination before you click it. This page never redirects on its own.

Choosing a password

The password is the entire security of the link. Anyone who finds the link — in a history file, a chat backup, a screenshot — has unlimited offline attempts at it. Minimum here is 12 characters, but bring more than the minimum.

This page deliberately does not generate one for you. Use a password manager's generator — 20 or more random characters — or roll physical dice against a Diceware list for something you can say out loud.

The strength meter reports an upper bound, never a guarantee. A password that reads as separated words is priced at 11 bits per word rather than per character, so a memorable phrase scores honestly low instead of scoring high for being long. Nothing here can recognise that a password is a song lyric or a reused one — only you know that.

There is no password recovery, but unlike encrypting a message, nothing is lost if you mistype: the destination is a page you already have. A link that will not open is simply a link to make again.

Relationship to /crypto

This page carries a destination URL. For arbitrary text — a note, a phrase, anything that is not a link — use /crypto, which encrypts up to 1 MiB and hands back a text block instead of a URL.

The two share a wire format exactly, so they interoperate: a payload lifted from one of these links decrypts on /crypto, and vice versa.

What this does not protect against

  • Anything already running on your device — malware, a hostile browser extension, or someone reading your screen.
  • Whoever you send the link to. Once they have the password, they have the destination, and they can forward both.
  • The destination site itself, which sees the visit like any other. It is not told the visit came from here.
  • Traffic analysis: the link reveals that a protected destination exists.
  • Passwords the browser or OS may have cached elsewhere. Fields here are marked no-autofill and no-spellcheck, and are wiped when you navigate away, but a JavaScript string cannot be reliably scrubbed from memory — that is a platform limit, not an oversight.

This browser does not expose the Web Crypto API on this page, so nothing here can run. Web Crypto requires a secure context — open this page over HTTPS.
